# 방 생성과 초대 입장 (#8)

## 현재 가능한 것

실제 서버 저장소에 방을 만들고 링크로 참가한다. 방 생성자와 첫 참가자를 같은 트랜잭션에 만들고 방장을 지정한다. 방은 게임과 별도다. [게임 설정 초안](game-settings.md)은 저장할 수 있으나 게임 생성·역할 선택·투표·과거 게임 열람 권한을 생성하지 않는다. 방장 이전·종료·접속 상태는 후속 이슈다.

- POST `/api/rooms`: `{nickname}`으로 생성
- POST `/api/rooms/:code/join`: `{nickname}`으로 입장
- GET `/api/rooms/:code`: 이미 참가한 브라우저의 방 조회
- 브라우저 주소 `/?room=초대코드`: 새 참가자는 신원 발급 후 닉네임 입력, 기존 참가자는 조회로 복귀

모든 API는 서버가 HttpOnly 쿠키를 검증한 신원만 사용한다. 요청에 sessionId·memberId·host를 넣을 수 없고 변경 요청은 동일 Origin·커스텀 헤더·JSON 검사 후 처리한다. 닉네임 하나 이외의 키를 거부한다. 응답은 방 ID, 초대코드, 자기 멤버 ID/방장 여부, 공개 닉네임 명단만 명시적으로 만든다. 세션 ID·토큰·게임 기록은 반환하지 않는다. 캐시는 no-store다.

## 닉네임과 재시도

닉네임은 NFKC 정규화, 앞뒤 공백 제거, 내부 연속 공백 한 칸 처리 후 1~20 유니코드 코드포인트다. 제어/포맷 문자는 거부한다. 중복 키는 소문자로 변환하므로 전각 영문·대소문자 차이로 중복을 우회할 수 없다. 유사한 모양의 모든 문자를 식별하는 보안 닉네임 시스템은 아니다.

활성 참가자에 대한 DB 유일성 제약과 immediate 트랜잭션으로 경합을 직렬화한다. 서로 다른 브라우저가 같은 이름을 동시에 제출하면 하나만 참가하고 나머지는 STATE_CONFLICT다. 이미 참가한 같은 브라우저의 재입장은 기존 참가자를 돌려준다. 다른 닉네임을 보내도 변경하지 않는다. 방 생성은 재시도 멱등성을 아직 제공하지 않으므로 응답 유실 때 자동 재전송하지 않는다. UI 중복 클릭 방지와 서버 참가 멱등성은 별개다.

## 링크·공개 범위

초대코드는 암호학적 난수 32바이트를 base64url로 표현한다(43자, 256비트). 링크를 아는 사람은 열린 방에 참가할 수 있으므로 링크는 초대하려는 사람에게만 공유한다. 링크 자체는 과거 게임 열람 권한이 아니다. 미참가 GET은 FORBIDDEN, 없는/잘못된/닫힌 방은 NOT_FOUND다. 닫힌 방 테스트는 DB fixture로만 만든다. 종료 API를 미리 구현하지 않는다.

현재 폴링·연결 끊김 감지는 [접속 감지](presence.md)에 따른다. 명시적 새로고침도 가능하다. 자동 퇴장·방장 이전은 후속 이슈다. 닉네임 복구, 다른 기기 신원 복구는 제공하지 않는다. 방 생성/참가 실패가 세션 삭제를 뜻하지 않는다.

## 검증 범위

단위 시험은 닉네임 경계, API 시험은 실제 쿠키·중복 경쟁·입력 사칭·CSRF·없는/닫힌 링크·게임 권한 미생성을 확인한다. 별도 임시 SQLite 시험은 방장 지정 중 실패 시 전체 롤백과 다시 연 DB 복귀를 확인한다. 실제 브라우저 다중 컨텍스트 시험은 3/5/6 브라우저가 하나의 방과 단일 방장을 보는지 확인한다. 이 시험은 전체 한 판 E2E 또는 외부 배포 검증이 아니다.

### 모바일 화면 확인

390px Chromium 모바일 에뮬레이션의 실제 방 화면을 `artifacts/rooms/room-mobile.png`로 캡처하고 직접 확인했다. 6명 명단·단일 방장 표시·초대 링크 복사·새로고침 버튼이 읽히며 가로 잘림은 없었다. 링크 입력은 한 줄이라 긴 주소는 입력 내부에서 이동한다. 현재 홈 소개 아래 대기실이 이어지는 긴 화면이며 별도 게임 화면 재배치는 후속 범위다. 실기기 키보드·안전영역 하드웨어 검증을 수행했다는 의미는 아니다.
