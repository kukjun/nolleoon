# 여행방 삭제와 복구 유예

승인된 규칙: 여행방은 자동 만료하지 않는다. 현재 관리자의 명시적 삭제 요청은 일반 접근을 즉시 차단하고, 7일 복구 유예 후 영구 삭제한다. 활성/준비 중 게임이 있으면 삭제를 거부한다. 마지막 관리자 탈퇴 등 다른 미결 정책은 바꾸지 않는다.

## API
- `POST /api/travel-rooms/:id/deletion`: `{requestId,expectedVersion,confirmation:"DELETE_ROOM"}`. 현재 관리자와 방 버전을 검사한다. `{roomId,deletionVersion,deletedAt,purgeAfter}`만 반환한다.
- `GET /api/travel-deleted-rooms`: 로그인한 원래 관리자에게 본인 유예방의 제목·원래 상태·위 응답 필드만 반환한다. 게임, 후보, 재판 이유, 명단은 반환하지 않는다.
- `POST /api/travel-rooms/:id/restore`: `{requestId,deletedAt,deletionVersion}`. `now < purgeAfter`이며 현재 관리자/계정/멤버십이 유효해야 한다. 원래 open/closed 상태만 복구한다. 이전 초대 링크는 재활성화하지 않는다.
- 같은 밀리초에 삭제→복구→재삭제해도 `deletionVersion`이 다르므로 오래된 복구 의도가 새 삭제에 적용되지 않는다.

유예 중 방/게임/이력/사진/초대의 일반 접근은 공통 저장소의 방 필터를 통해 차단된다. 계정 탈퇴로 제거한 프로필이나 멤버십을 방 복구로 생성하지 않는다. 휴지통에서 기한이 지난 방을 숨기는 것은 실제 purge 완료를 뜻하지 않는다.

## 영구 삭제 범위와 실행
내부 `purgeExpired(roomId)`는 해당 방의 게임 JSON·결과·참가 연결·여행방 요청 영수증·초대·presence·멤버십·방을 한 트랜잭션으로 제거한다. 계정, 개인 프로필 사진, 독립 레거시 원본은 삭제하지 않는다. 다른 방은 보존한다. SQLite 백업/저장매체의 물리적 즉시 소거를 주장하지 않는다.

`RoomDeletionMonitor`는 애플리케이션 시작과 60초마다 만료방을 100개씩 처리한다. 서비스가 꺼져 있으면 다음 기동에서 처리한다. 실제 서버 시계가 기한에 도달하면 API 복구는 즉시 거절한다. 시험에서는 monitor를 끌 수 있고 종료 시 interval을 제거한다. OS 스케줄러/운영 서비스 변경은 이 구현의 범위가 아니다.

## 오래된 백업의 부활 방지
삭제/복구/purge마다 별도 durable ledger에 먼저 기록하고 SQL을 적용한다. `RoomDeletionLedger` 미주입 상태에서는 삭제/복구를 503으로 차단한다. 외부 최신 ledger/anchor를 실제로 구성해야 운영에서 사용할 수 있다. 이 변경은 운영 파일을 만들거나 초기화하지 않았다.

`applyRoomDeletionEvent`는 검증된 순서의 이벤트를 별도 복원 복사본에 적용하는 진입점이다. 적용 ID를 저장하여 멱등 처리하며 없는 방·계정·멤버십을 재생성하지 않는다. 방 이벤트를 적용한 후 계정 삭제 증거를 최종 적용해야 계정 정보가 부활하지 않는다. 원장 기록 후 SQL 실패 시 원장 이벤트는 남고 다음 요청/시작 정리가 우선 재적용한다. 원장이나 anchor 검증 실패를 무시하고 접근시키면 안 된다.

## 검증 범위
합성 HTTP/SQLite 시험으로 관리자/CSRF 공통경계, 즉시 차단, 7일 정확경계, ABA, 원래 closed 상태 복구, 탈퇴 계정 불변, purge 범위·rollback, 재기동 정리, 원장 우선 적용을 검증한다. timer시험은 주기/종료/실패 로그를 검증한다. 실제 운영 삭제, 7일 실시간 대기, 물리 매체 소거는 실행하지 않았다. schema15(계정 삭제) 뒤 schema16에 의존한다.
