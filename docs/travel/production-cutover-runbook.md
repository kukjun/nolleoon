# 새 여행방 운영 전환 런북

사용자가 기존 놀러온 주소에 새 버전과 실제 Kakao 로그인을 적용하도록 요청했다. 기존 익명 링크·기록은 유지하고 새 여행방 진입을 명확히 한다. 날짜 UI는 추가 지시 없이 변경하지 않는다.

## 고정할 것

- 독립 검토한 exact RC, build artifact, 실제 실행 Node/의존성.
- 기존 공개 origin·포트·터널 유지. 승인된 기존 Kakao 비밀 파일을 서버에서만 읽고 값·callback query·cookie를 로그에 남기지 않는다.
- 내부 DB와 별도 물리 볼륨의 authoritative 계정/방 삭제원장·현재 unlink큐/terminal witness. 해당 authority는 DB snapshot 복원으로 덮지 않는다.
- authority가 누락되거나 이미 관찰한 prefix보다 뒤로 가면 기동·요청·unlink를 막는다. 전체 디스크와 authority가 동시에 과거로 되돌아가는 것을 로컬 코드가 증명한다고 주장하지 않는다.

## 비파괴 사전 준비

1. 현재 공개 API/HTML과 활성 판/접속을 확인한다. 진행 판이 있다면 중단시키지 않고 전환을 기다린다.
2. 승인된 온라인 백업으로 원본을 보존한다. 별도 비공개 복사본에만 schema migration을 적용하고 기존 모든 열·행·이미지/세션 보존 및 integrity/FK를 검증한다. 실제 운영 snapshot schema11→17의 23개 기존 테이블 보존 리허설은 이미 통과했으며 새 RC/schema에 재실행한다.
3. 현재 운영 schema에 새 account/delete authority 이력이 없음을 확인한 최초 전환에만 새 전용 authority를 명시 초기화한다. 누락 파일을 자동 빈 원장으로 복구하지 않는다.
4. 새 DB 복사본으로 loopback 전용 사전기동, 기존/새 static/API, 잘못된Origin·인증·개인정보 비노출을 검증한다. 임의 실제 사용자 탈퇴/unlink는 하지 않는다.
5. 일일 백업·상태 관측을 준비한다. 저장 공간 예산은 경보용이며 임의 데이터를 삭제하는 quota가 아니다. 만료 백업은 기본 보고만 하고 무승인 영구 삭제하지 않는다.

## 전환과 복구

- 전환 직전 활성 판을 다시 확인하고 기존 프로세스를 정지한 뒤 최종 일관 snapshot에서 새 운영 DB를 만든다. old DB·old release·old service definition은 보존한다. 원본 파일을 in-place down-migrate하지 않는다.
- 새 버전/새 DB/고정 authority/비밀 파일을 연결해 동일 포트로 시작한다. 새 데이터를 받기 전 실패하면 공개되지 않은 후보만 보존하고 이전 구성을 재개한다.
- 공개 후 쓰기가 발생하면 이전 DB로 무조건 되돌리지 않는다. 새 데이터와 삭제 의도를 보존하고 필요하면 일시 중단/유지보수 상태에서 호환 RC로 roll-forward한다. 이전 바이너리를 최신 schema에 억지로 실행하지 않는다.
- 실제 HTTPS/새 여행방 화면/기존 초대/정적 자산/카카오 로그인 시작·callback 구성/세션·권한을 확인한다. 자동화 합성 provider와 실제 Kakao 성공, Chromium viewport와 물리 기기를 구분한다.

## 7일 unlink의 운영 의미

앱 탈퇴 후 현재 큐의 Kakao 식별자만 최대7일 재시도에 사용하고, 성공/기한 만료 시 원문과 매핑을 제거한다. 처리 중 재가입을 막는다. 만료 뒤 자동 재시도는 하지 않으며 비식별 상태만 운영 확인 대상으로 남긴다. 종료된 오래된 작업을 DB 복원으로 재실행하지 않는다. 기기/프로세스가 정지한 동안 물리 파일을 삭제할 수 있다고 약속하지 않으며, 재기동 시 요청/원격 호출 전 만료 정리가 필수다.

## 남은 검증 표시

실제 Admin key 공급/앱 권한과 실제 승인 시험 계정의 unlink는 합성 시험이 대체하지 않는다. 원격 CI·물리 기기 접근 제한은 별도 기재한다. FileVault 해제 전·로그아웃·절전·외장장치 누락·네트워크 단절에도 무중단 서비스가 가능하다고 보장하지 않는다.
