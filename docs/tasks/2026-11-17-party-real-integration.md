# PARTY-21/22 · 실제 아바타와 연속 게임 인수

범위: 테스트 전용 독립 worktree, 로컬4184·임시 SQLite. 운영 DB/포트/권한/정책 변경 없음. 모든 사용자명·이미지는 합성이다.

## 추가 검사
- 실제 브라우저 3명+외부인1명: 프리셋 저장·새로고침, 실제 사진 업로드/crop, 서버 WebP/64KiB bound/no-store, 같은 방 두 사람에게 동일 SHA-256 이미지 표시, 외부인 map/image403, 실제 재판 결과까지 동일사진, 방닫힘 후 map/image410·화면기본이미지·본인profile유지.
- 같은 actor 병렬 avatar CAS 두 요청 중 성공1/충돌1, 잘못된 PNG 업로드 실패 후 기존프로필불변.
- 네트워크 route mocking 없음. 실제 Nest/SQLite/Sharp/세션 쿠키를 사용한다.

## 실행
초기 아바타 마지막assert는 닫힌 방의 명단이 정상적으로0명인 상태에서 과거멤버row를 찾아 실패했다. 보호동작을 완화하지 않고 실제 남아있는 결과상단의 자기아바타에서 fallback을 확인하도록 locator를 수정했다. 이후 아바타2개 통과(11.7초+0.257초). 최종정적 lint는 browser crypto 전역을globalThis로 명시한 뒤 다시 확인한다.

## 한계
이 검사는 Chrome desktop 기반 모바일 viewport다. 실기기, 외부접속, 운영부하/지속 soak, quota한계까지 대량DB채우기를 하지 않았다. 기존 업로드크기·전체quota 단위/API시험을 대체하지 않는다. 단절사진 회수는 미래요청 권한취소이며 수신자가 이미 저장한 이미지를 회수하는 기능이 아니다.

## 세 게임 연속 E2E
`party-journey-e2e.spec.mjs`의 `@party-e2e`1개: 실제3contexts/하나의invite에서 팀2/1 균형결과 → next → 각자배정제비1장, 당첨2명 → next → 방장피고·벌칙수락·변론·익명투표·유죄집계 → 개인이력3종. 주요행동 모두 UI, 결과/배정/API모킹 없음. 실제실행21.9초 PASS. 진행중타인투표이유미노출·결과이유작성자/아바타미연결도 검사한다. 기존 legacy E2E3개를 대체하지 않는다.

## 320px 판결 우선 배치 회귀 수정
기존 결과 상단 아바타가 집계 영역을 y=212px까지 밀어내던 문제를 실제 아바타 E2E에 `집계 결과 top < 180px` 조건으로 추가해 RED를 재현했다. 기준을 완화하지 않고 집계/판결을 먼저, 자기 아바타를 그 아래에 배치했다. 사진 유지·접근 통제 검사는 그대로 유지한다.

최종 실행: build, 전체 ESLint, typecheck PASS. 실제 아바타2개 + 세 게임 연속 E2E1개 모두 PASS(총34.8초). 320×740 결과 스크린샷 `artifacts/party-security/real-photo-result-320.png`를 실제 픽셀로 확인했다. 이 변경은 배치 순서만 바꾸며 집계·벌칙·익명성 정책을 변경하지 않는다.
