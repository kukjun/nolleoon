# #189 기존 웹 브라우저 gate 진단

## 관찰과 경계

제품 코드와 운영 서버는 변경하지 않았다. 기존 Playwright는 workers=1, retries=0, 기본 테스트 제한 15초다. 기존 전체 75개 진단은 10.2분(약612초), 71 PASS/4 timeout이었다. 360초 단일 stage는 이 측정량을 수용하지 못한다. 공유 Mac의 다른 작업은 종료하거나 설정을 바꾸지 않았다.

실패한 4개만 동일 trace 설정으로 비교했다.

| 조건 | 닫기 | 다음 준비 | 완료 결과 복구 | 401 복구 | 전체 |
|---|---:|---:|---:|---:|---:|
| Flutter 병행 부하 | timeout 15.282s | 11.209s | 9.881s | 12.008s | 56.645s |
| Flutter 실행을 멈춘 창 | timeout 15.164s | 11.381s | 10.234s | 11.977s | 53.680s |
| 준비/관찰 순서 개선 | 8.378s | 7.563s | 7.512s | 8.147s | 33.633s, 4 PASS |

trace에서 해당 준비 중 API GET은 약6–17ms였고 UI 클릭·렌더 안정화(약0.1–0.4초), 참가자별 폴링 관찰(약0.8–2.4초)이 누적됐다. 닫기 실패는 필요한 3.2초 무-heartbeat 관찰 중 전체 테스트 시간이 소진됐다. 따라서 부하만 탓하거나 제품 API에 근거 없이 지연 결함을 지정하지 않는다. 이 표는 제한된 로컬 관찰이며 보편적 성능 보장이 아니다.

## 변경한 테스트 실행 방식

- 세 파일의 동일한 실제 UI 준비를 `readyVotingCourt`로 모았다. 두 독립 참가자의 입장은 병렬 I/O로 실행하되 각 실제 로비 표시를 추가 확인한 후 방장을 새로고침한다. 실제 브라우저 신원·가입·역할·설정·동의·투표 시작은 API fixture로 대체하지 않았다.
- 같은 설정 단계의 중복 재클릭만 없앴다. 첫 단계 진입·실제 입력/저장 확인 및 나머지 시나리오의 권한·privacy·결과·복구 assertions는 유지한다.
- 방장 닫기 완료 직후 3.2초 무-heartbeat 관찰을 시작하고, 독립적인 참가자/외부인/화면 검증을 그 관찰 창 안에서 수행한다. 3.2초 완료 자체와 heartbeat=0을 모두 확인한다. 시간을 줄이거나 가짜 시계로 바꾸지 않았다.
- 준비 실패 시 이미 만든 guest contexts도 정리한다.

## 전체 gate 예산 변경 (명시적)

단일360초에서 **두 순차 shard ×360초 = 총 최대720초**로 바뀐다. 이는612초 실측에 약18% 여유를 두는 실행 계획 변경이다. 각 stage의360초, runner 전역최대360초, 개별15초(기존 명시적30초 시나리오 포함), worker1, retries0, skip 거부는 그대로다. 병렬 stage로 Mac 부하를 늘리지 않는다.

Playwright 내장 `--shard=1/2`, `--shard=2/2`와 동일 grep-invert를 사용한다. 계약 시험이 원래75 test/project ID 집합과 두 shard 합집합을 실제 `--list`로 비교하고 중복·누락·skip 예상 상태를 거부한다. 두 stage가 모두 성공해야 전체 성공이다. `npm run test:browser` 단독 명령은 원래 전체 suite를 실행한다.
