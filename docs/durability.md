# 재시작과 데이터 내구성

## 영속 상태와 복구 순서

서버가 다시 시작하면 같은 DB의 세션 hash, 방과 초안, 역할·수락 revision, 시작/투표/다음 준비 영수증, 동결된 투표 대상과 판결 기록을 읽는다. 브라우저 쿠키가 그대로 있고 만료되지 않았다면 같은 신원이다. DB 복원은 삭제된 브라우저 쿠키를 복원하거나 다른 브라우저에 접근권을 주지 않는다.

두 독립 monitor는 시작 시 즉시, 이후 1초 간격으로 동일한 유지 작업을 실행한다. 요청 경계도 같은 작업을 거친다. 이미 저장된 `disconnectedAt + 600000`을 퇴장 효력 시점으로 사용한다. 투표 마감이 피고 퇴장 시각보다 앞서거나 같으면 먼저 정산하고, 퇴장이 먼저면 미완료 게임을 중단한다. 동률 뒤 중단은 기존 1차 정산을 DB에 보존하지만 공개 범위는 #33 결정 전까지 보수적으로 가린다. 최종 판결까지 끝났다면 이후 퇴장이 판결을 중단으로 바꾸지 않는다.

중단 전에 단절을 **감지하지 못한** 연결은 서버가 다시 동작하며 감지한 시점부터 10분이다. 마지막 heartbeat부터 임의로 소급 퇴장시키지 않는다. 서버가 내려간 동안 UI가 즉시 갱신되거나 타이머 작업이 실행됐다고 주장하지 않는다. 재시작 후 저장된 마감 시각으로 조정할 뿐 투표 시간을 연장하지 않는다.

## 커밋과 장애의 한계

짧은 SQLite IMMEDIATE transaction 안에서 표와 마지막 표 정산, 퇴장과 방장 이양 등의 원자성을 유지한다. API 성공 응답을 받기 전에 연결이 끊기면 이미 커밋됐을 수 있다. 새 요청 ID로 의도를 바꾸지 말고 원래 명령의 멱등 영수증을 확인한다. 프로세스가 종료된 미커밋 transaction은 복구 시 rollback된다.

선택한 런타임을 합성 임시 파일로 직접 확인한 값은 SQLite 3.54.1, journal_mode WAL, synchronous 2(FULL)이다. 프로세스 강제 종료 시험은 전원 차단, 고장 난 디스크·컨트롤러, 파일시스템 오류와 같은 의미가 아니다. 디스크 여유, 실제 호스트/볼륨과 fsync 동작까지 검증했다고 주장하지 않는다. checkpoint는 별도 백업이 아니며 WAL 삭제나 실행 중 본체 파일만 복사하는 것은 복구 절차가 아니다.

## 백업·운영 경계

[온라인 백업과 새 경로 복원](sqlite-backup.md)을 사용한다. 자동 주기·보관 삭제 정책은 아직 없으며 수동 백업이다. 마지막으로 검증된 백업 이후의 커밋은 그 백업으로 복원하면 사라질 수 있다. 복원 시험은 실제 서비스 경로 전환·운영 프로세스 종료를 하지 않는다. 운영 전환과 실제 외부 배포는 별도 작업이다.

DB와 백업에는 민감한 게임 내용, 토큰 hash, 초대 식별자가 포함될 수 있다. 정적 웹 루트·공개 저장소·공유 폴더에 두지 않는다. 접근 가능한 전용 위치와 충분한 여유 공간은 운영자가 확인해야 한다. 도구는 권한 설정을 자동 변경하거나 암호화·원격 보관·삭제를 약속하지 않는다. 백업 CLI의 정규화된 오류에는 DB 내용, 쿠키, SQL 인수 또는 백업 경로를 출력하지 않는다. 기존 모든 실행 환경의 표준 오류 수집·보관까지 감사한 것은 아니다.

## 검증 기록

실제 실행한 process/API/DB 시험의 결과와 미실행 항목은 작업 기록과 최종 clean source 하네스 보고서에 남긴다. synthetic 임시 DB 및 직접 생성한 자식 프로세스만 사용하며 기존 서비스나 사용자 DB를 중단하지 않는다. 브라우저 시험을 새로 추가하지 않는 대신 기존 전체 회귀는 최종 독립 하네스에서 실행한다.

이번 회귀는 처음 자식 실행 파일 부재로 RED를 확인한 뒤, 실제 Nest 자식 프로세스와 SQLite usecase의 쓰기 직후 IPC 장벽에서 SIGKILL을 수행한다. 표 저장·마지막 표 정산·방장 이양 각각 미커밋 상태를 확인하고 재기동 뒤 전체 기록 비교와 재시도를 검사한다. 시작 monitor의 마감/만료 전후·동시 시각, 599999/600000ms 유예 및 최초 단절 감지 시각도 고정된 서버 시계로 검사한다. 실제 10분 대기 시험이나 실제 전원 차단은 아니다. 합격 개수와 최종 소스 상태는 최종 실행 보고서를 따른다.

완료된 합성 게임은 온라인 백업→별도 새 DB 복원 후 실제 새 Nest 프로세스로 열어, 원래 쿠키의 개인 이력 HTTP 200 응답이 동일한지도 검사한다. 원본 서버의 경로나 파일은 바꾸지 않는다. 마지막 검증은 이 버전의 합성 데이터 복원이지 실제 운영 백업을 검증했다는 뜻이 아니다.
